CLAUDE INSTRUCTIONS

Purpose
- Apply these standards to every project and every change.
- Use specialized skills/tools proactively when they match the task; suggest them instead of blocking on them.

A. Principles to Apply at All Times (Decision Filters)
1) No speculative features
   - Do not add features, flags, or configuration unless users actively need them.

2) No premature abstraction
   - Do not create utilities until you have written the same code three times.

3) Clarity over cleverness
   - Prefer explicit, readable code over dense one-liners.

4) Justify new dependencies
   - Treat every dependency as attack surface and maintenance burden. Add only with a clear reason.

5) No phantom features
   - Do not document or validate features that are not implemented.

6) Replace, don’t deprecate
   - When a new implementation replaces an old one, remove the old one entirely.
   - Do not add shims, dual config formats, or migration paths.
   - Proactively flag dead code.

7) Verify at every level
   - Add automated guardrails first (linters, type checkers, pre-commit hooks, tests).
   - Prefer structure-aware tools (AST/LSP/compilers) over text pattern matching.
   - Review your own output critically; assume every layer will miss something.

8) Bias toward action (with stated assumptions)
   - Decide and move on anything easily reversible; state your assumption.
   - Ask before committing to interfaces, data models, architecture, or destructive/write ops on external services.

9) Finish the job (without inventing scope)
   - Don’t stop at the minimum that technically satisfies the request.
   - Handle visible edge cases, clean up what you touched, and flag adjacent breakage.
   - Do not gold-plate or create new scope.

10) Agent-native by default
   - Design so agents can achieve any outcome users can.
   - Tools are atomic primitives; features are outcomes described in prompts.
   - Prefer file-based state for transparency and portability.
   - For any UI capability, ensure an agent can achieve the same outcome.

B. Code Quality Requirements (Non-Negotiables)
1) Hard limits
   - <= 100 lines per function
   - Cyclomatic complexity <= 8
   - <= 5 positional parameters
   - 100-character line length
   - Absolute imports only (no relative “..” paths)
   - Google-style docstrings for non-trivial public APIs

2) Zero warnings policy
   - Fix every warning from every tool (linters, type checkers, compilers, tests).
   - If a warning truly can’t be fixed: add an inline ignore with a justification comment.
   - Never leave warnings unaddressed.

3) Comments discipline
   - Code should be self-documenting.
   - No commented-out code (delete it).
   - If you need a comment to explain WHAT the code does, refactor for clarity.

4) Error handling standard
   - Fail fast with clear, actionable messages.
   - Never swallow exceptions silently.
   - Include context: operation, input, and suggested fix.

C. Review Workflow (How to Evaluate Code)
1) Before reviewing
   - Sync to latest remote: git fetch origin

2) Evaluate in this order
   - Architecture -> Code quality -> Tests -> Performance

3) For each issue you find
   - Describe concretely with file:line references.
   - Provide options with tradeoffs when the fix isn’t obvious.
   - Recommend one option.
   - Ask before proceeding.

D. Testing Workflow (How to Write and Validate Tests)
1) Test behavior, not implementation
   - Tests should verify what code does, not how.
   - If a refactor breaks tests but behavior is unchanged, the tests were wrong.

2) Test edges and errors (not only the happy path)
   - Include empty inputs, boundaries, malformed data, missing files, network failures.
   - Every handled error path must have a test that triggers it.

3) Mock boundaries, not logic
   - Mock only: slow (network/filesystem), non-deterministic (time/randomness), or external services you don’t control.

4) Verify tests catch failures
   - Break the code, confirm the test fails, then fix.

E. Development Guardrails (Setup and Maintenance Rules)
1) Versions and dependencies
   - When adding dependencies, CI actions, or tool versions: look up the current stable version.
   - Do not assume versions from memory unless the user provides one.

2) Bash scripts
   - Every bash script must start with: set -euo pipefail

3) GitHub Actions
   - Pin actions to full SHA with a version comment: actions/checkout@<full-sha>  # vX.Y.Z
   - Use persist-credentials: false
   - Configure Dependabot: 7-day cooldowns + grouped updates

F. Day-to-Day Working Workflow (From Change to PR)
1) Plan (lightweight)
   - Restate the goal and constraints.
   - Identify what is reversible vs. what commits you to an interface/data model/architecture.
   - If it commits to an interface/data model/architecture or touches external services destructively: ask first.

2) Implement
   - Keep changes minimal and directly tied to the request.
   - Avoid speculative features and premature abstractions.
   - Prefer readability and explicitness.
   - Keep within hard limits; refactor if you exceed them.
   - Add/adjust tests that validate behavior and error paths.
   - Ensure error handling is actionable and contextual.

3) Verify (multi-layer)
   - Run the relevant linters/type checker; fix all warnings.
   - Run relevant tests (not necessarily the full suite) that cover your change and its edges.
   - Review your own diff for unnecessary complexity, redundancy, and naming clarity.

4) Before committing (required checklist)
   - Re-read changes for unnecessary complexity, redundant code, and unclear naming.
   - Run relevant tests (not the full suite).
   - Run linters and type checker; fix everything.

5) Commit rules
   - Imperative mood subject line, <= 72 characters.
   - One logical change per commit.
   - Never amend/rebase commits already pushed to shared branches.
   - Never push directly to main; use feature branches and PRs.
   - Never commit secrets/credentials; use .env (gitignored) and environment variables.

6) Hooks and worktrees (parallel work)
   - If using parallel subagents: each subagent must use its own worktree (wt switch <branch>).
   - Never share working directories with parallel subagents.

7) Pull request rules
   - Describe what the code does now (what’s in the diff).
   - Do not include discarded approaches or prior iterations.
   - Use plain, factual language.
   - Avoid hype words: critical, crucial, essential, significant, comprehensive, robust, elegant.

End of workflow.
