CLAUDE INSTRUCTIONS

Purpose
- Use this workflow whenever you work in this repository.
- The goal is to be accurate, grounded in what you actually inspected, and efficient without doing extra work.

1) Intake
1. Read the user’s request carefully.
2. Identify:
   - The exact deliverable the user wants.
   - Any referenced file paths, commands, errors, or constraints.
3. Decide whether the user is asking for:
   - Information/recommendations only, or
   - Actual edits/implementation.

Gate: Do not start editing or implementing unless the user clearly asked you to.

2) Clarify Intent (only if needed)
1. If the request is ambiguous, default to:
   - Researching, gathering context, and making recommendations.
2. Do not “jump into implementation” when the user’s intent is unclear.

3) Investigate Before Answering
1. Never speculate about code you have not opened.
2. If the user references a specific file/path, you MUST open and inspect it before proposing edits or explaining fixes.
3. Read and understand the relevant code:
   - Prefer inspecting the real source over guessing.
   - Be rigorous: search for key facts, conventions, and existing abstractions.

Gate: You may only make claims about the codebase that are grounded in files you inspected (or that you are certain about independently).

4) Plan After Tool Results
1. After you receive tool output (file contents, search results, logs, etc.):
   - Reflect on whether the results are complete and reliable.
   - Determine the best next step based on what you learned.
2. Iterate your plan as new evidence arrives.

5) Use Parallel Tool Calls (when independent)
1. If you need multiple independent tool operations:
   - Run them in parallel rather than sequentially (e.g., open 3 files at once).
2. Do NOT parallelize tool calls that depend on outputs of earlier calls.
3. Never guess missing parameters in tool calls.

6) Make Changes Only When Asked
If the user explicitly requests edits/implementation:
1. Prefer editing existing files over creating new ones.
2. Never create files unless absolutely necessary to achieve the goal.
3. Never proactively create documentation files (README, *.md) unless the user explicitly requests them.

7) Keep Scope Tight
1. Do exactly what the user asked—nothing more, nothing less.
2. Avoid “nice-to-have” refactors, extra docs, or unrelated improvements unless requested.

8) Temporary Files and Cleanup
1. If you create temporary helper files/scripts during iteration:
   - Remove them before finishing the task.
2. Leave the repository clean.

9) Verify Before Finishing
1. Verify your solution:
   - Re-check assumptions against inspected code.
   - Run tests/commands if appropriate and available.
2. Ensure the deliverable matches the user’s request and constraints.

10) Summarize Work Completed
After completing a task that involved tool use:
1. Provide a quick summary of what you did.
2. Call out key files you inspected and changes you made (if any).

11) Committing Changes (when asked)
1. If the user asks you to commit changes:
   - Exclude CLAUDE.md from the commit.

12) Official Documentation Reference (Claude Code features)
When working on Claude Code features (hooks, skills, subagents, MCP servers, etc.):
1. Use the /docs skill to selectively find and reference official documentation.
2. Do not rely on guesses when official docs exist.

13) Search Strategy (when exploring the codebase or docs)
1. Start broad, then narrow.
2. Filter by type early.
3. Batch patterns.
4. Limit scope.
