CLAUDE INSTRUCTIONS

Purpose
- This workflow is for mission-critical infrastructure where mistakes can cause business loss.
- Default stance: defensive. Zero tolerance for broken builds, missing tests, placeholders, or swallowed errors.

0) Operating Mode: Zero Tolerance
- You do not proceed with any of the following present:
  - Broken builds or failing tests
  - Stub / placeholder implementations (e.g., raise NotImplementedError, throw new Error(“not implemented”), “Coming soon”, dummy outputs)
  - Commented-out code (use Git history instead)
  - Skipped or commented-out tests
  - Any stub/fallback implementations that pretend to work
  - Swallowed errors (e.g., empty catch {} blocks, bare except: pass, rescue => nil)
- If you cannot implement correctly: STOP and ask for help rather than stubbing.

1) Working Directory Discipline (Non-Negotiable)
- Always run commands from the repository root directory.
- Never use “cd” unless you are explicitly debugging a submodule.
- Assume all build and test commands are designed to run from repo root.

2) Security & Safety Gate (Before You Touch Anything)
2.1 Sensitive data check
- If you detect API keys, passwords, tokens, or other sensitive data:
  - Abort immediately.
  - Explain what was detected.
  - Request a sanitized prompt/input before continuing.

2.2 Crash policy (CRITICAL)
- Any unhandled crash is treated as a severe bug.
- The application must return errors gracefully; it must never crash.
- If a crash occurs:
  - FIRST fix the validation/error-handling path that allowed the crash.
  - THEN fix the bug that originally triggered it.

3) Work Loop (TDD First; Always Verified)
Repeat this loop for each change (feature, refactor, bug fix):

3.1 Specify (Tests First)
- Write or update tests that define the intended behavior.
- Tests are the contract. Prefer direct, explicit setup.

3.2 Prove tests fail for the right reason
- Run tests from repo root.
- Confirm new/changed tests FAIL before you implement.
- If they pass unexpectedly, the test is not specifying new behavior; fix the test.

3.3 Implement (No placeholders; no error swallowing)
- Implement the behavior completely.
- Do not add stubs or “temporary” implementations.
- Do not ignore errors; every error must be handled explicitly or propagated.
- Clean up resources: always pair acquisition with cleanup/release.

3.4 Verify build + tests for every code change
- For EVERY code change (exception: documentation-only .md changes):
  - Run the build and the full test suite as required by the repo.
- Do not consider work “done” until build and tests are green.

3.5 Handle failures immediately
- Any failing test or build break is treated as top priority:
  - Stop new work.
  - Fix the failure.
  - Re-run build/tests until green.

4) Debugging Workflow (Evidence-Based)
- If a bug is not obvious:
  - Improve visibility first (instrumentation, logs, asserts, targeted prints).
  - Only then attempt to change logic.
- Use evidence-based debugging only:
  - Form a hypothesis
  - Add observability to validate it
  - Confirm with test output
  - Fix and re-run

5) Coding Standards Checklist (Apply During Implementation)
- Control flow:
  - Prefer minimal “else” statements.
- Naming:
  - Use descriptive variable names (top, value, operand not a, b).
- Imports:
  - Use direct imports (no aliases).
- Assertions:
  - Assertions must include descriptive messages.
- Cleanup:
  - Always pair resource acquisition with cleanup/release.

6) Testing Philosophy (How Tests Should Look)
- Tests must be self-contained:
  - No abstractions for test setup.
  - No helper functions; copy/paste setup is preferred.
- Test output rule:
  - Always print test results.
  - If tests produce no output, they PASSED successfully.
  - Only failed tests should produce output.
- Failure response:
  - Any test failure must be fixed immediately before continuing.

7) Collaboration Workflow
- When proposing a change in architecture/approach:
  - Present a proposal.
  - Wait for approval before implementing.
- If your plan fails or you hit uncertainty:
  - STOP.
  - Explain what happened and what you learned.
  - Wait for guidance.

End State (Definition of Done)
- Code changes:
  - Fully implemented (no placeholders/stubs)
  - No swallowed errors
  - No crashes; validation prevents crash paths
  - Build succeeds from repo root
  - Tests pass; failures fixed immediately
- Documentation-only changes:
  - Allowed to skip build/test per exception, but do not introduce code changes.
